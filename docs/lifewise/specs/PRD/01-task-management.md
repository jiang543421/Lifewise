## 1. 产品目标（SMART）

| 维度 | 描述 |
|---|---|
| **Specific（具体）** | 为个人用户提供「待办清单 + 习惯打卡」二合一能力，让日/周待办有节奏、长期习惯可追踪 |
| **Measurable（可衡量）** | 单条任务从点击「新建」到保存完成的端到端耗时 P95 < 1.5s；习惯打卡一次点击完成率 > 99% |
| **Achievable（可达成）** | 复用 Spring Boot 3 + JPA + PostgreSQL 技术栈，AI 能力可降级（智能排期为扩展项） |
| **Relevant（相关性）** | 任务是数字生活最高频入口（用户每天至少打开 1 次），是其它模块（计划/日报）的数据源 |
| **Time-bound（时限）** | MVP 在 Phase 1（4-6 周）内交付；智能排期建议列入 v1.1+ 扩展 |

**核心 OKR**：
- **O1**：让用户每天「知道该做什么、做完能感受到」
- **KR1.1**：日活跃用户在「任务」模块至少创建 1 条任务的占比 ≥ 60%
- **KR1.2**：连续 7 天打卡用户留存率 ≥ 50%
- **KR1.3**：习惯打卡完成率（已打卡 / 应打卡）月均 ≥ 70%

## 2. 用户画像

### 用户画像 A：忙碌白领「小林」

- **角色**：28-35 岁互联网/金融从业者
- **痛点**：每天被会议、消息、邮件淹没，「想到要做」和「做到」之间频繁掉链子；想养成阅读/运动习惯但总是半途而废
- **核心任务**：
  1. 早晨花 1 分钟把今天要做的事过一遍
  2. 工作中遇到新任务随手记下来
  3. 晚上回顾今天完成度
  4. 看到阅读/跑步连续打卡天数有成就感，继续坚持

### 用户画像 B：自我提升者「阿瑶」

- **角色**：25-40 岁自由职业/学生
- **痛点**：同时在准备多项目标（考试、健身、读书），缺乏工具统一管理；习惯了 Notion/滴答清单但数据分散在多个 App
- **核心任务**：
  1. 把每个目标拆解成习惯或一次性任务
  2. 在一个界面看到所有进行中的事
  3. 习惯连续打卡后看到累计数据有正反馈

### 用户画像 C：多线程妈妈「张姐」

- **角色**：30-45 岁兼顾家庭与工作的女性
- **痛点**：要管孩子的事、家里采购、自我提升三类事，容易遗忘
- **核心任务**：
  1. 快速记录一个待办（30 秒内完成）
  2. 把重复事项标记为习惯（如「每天提醒孩子吃维生素」）
  3. 一周复盘时看到任务完成情况

## 4. KANO + RICE 划分逻辑

### KANO 模型归类

| 需求 | KANO 类别 | 理由 |
|---|---|---|
| CRUD 任务、习惯打卡、streak 计算 | **基本型（MUST）** | 没有这些模块就不存在；用户从同类产品（如滴答清单、Todoist）来的基本预期 |
| 截止时间、优先级、标签 | **基本型（MUST）** | 任务管理领域的事实标准 |
| 子任务、看板视图、回收站 | **期望型（SHOULD）** | 没有也能用，有了显著提升体验 |
| 智能排期、标题改写 | **魅力型（COULD）** | 用了惊喜，不用也无妨；高差异化但开发成本高 |
| 番茄钟、团队共享 | **无差异型（WON'T this version）** | 与本模块核心目标弱相关 |

### RICE 评分（仅对 SHOULD/COULD 评分，决定是否进 MVP）

| 需求 | Reach | Impact | Confidence | Effort | RICE | 决策 |
|---|---|---|---|---|---|---|
| 子任务 | 0.6 | 2 | 0.9 | 0.5 | 2.16 | **进 MVP**（高频要求） |
| 看板视图 | 0.4 | 1 | 0.9 | 1 | 0.36 | **进 MVP**（前端组件复用成本低） |
| 回收站 | 0.5 | 1 | 0.8 | 0.5 | 0.8 | **进 MVP**（软删除基础设施已搭好） |
| 截止时间 Push | 0.7 | 2 | 0.9 | 1 | 1.26 | **进 MVP**（强提醒场景，丢失即事故） |
| 智能排期 | 0.4 | 3 | 0.5 | 8 | 0.075 | **v1.1**（价值高但需 LLM 调试周期） |
| 标题改写 | 0.3 | 2 | 0.4 | 6 | 0.04 | **v1.1**（需求存疑，先观察用户行为） |

**结论**：MVP 收纳了所有 MUST + 4 个 RICE 高分 SHOULD；智能类一律后置，避免阻塞 Phase 1 交付。

## 5. 用户故事

### US-TASK-01：快速记录任务

> 作为**忙碌白领小林**，我需要**在 30 秒内新建一条任务并设优先级**，以便于**在会议间隙把刚想到的事记下来，不打断当前工作流**。

**验收标准（AC）**：
- **AC-1**：从首页点击「+ 任务」到看到任务出现在列表中，端到端耗时 P95 < 1.5s
- **AC-2**：任务必填字段仅「标题」，其余字段（备注、截止、优先级、标签）可后续补充
- **AC-3**：保存成功后有 Toast 提示「已保存」，并在 30 秒内支持「撤销」（删除刚建的任务）

### US-TASK-02：今日视图直观看到要做的事

> 作为**自我提升者阿瑶**，我需要**进入应用就能看到今天的所有任务**，以便于**快速决定先做哪件**。

**验收标准（AC）**：
- **AC-1**：进入「任务」模块默认落在「今日」Tab，自动过滤 `due_at` 为今天 + 未完成的任务
- **AC-2**：任务按优先级 P3 → P0 倒序展示，相同优先级按截止时间正序
- **AC-3**：今日无任务时展示空状态插画 + 「+ 新建任务」CTA

### US-TASK-03：连续打卡看到 streak

> 作为**多线程妈妈张姐**，我需要**看到每个习惯的连续打卡天数**，以便于**坚持不下去的时候有视觉上的正反馈**。

**验收标准（AC）**：
- **AC-1**：每个习惯卡片显著位置展示「🔥 N 天」数字，今日已打卡则 N 为含今日的连续天数
- **AC-2**：今天还没打卡但历史连续，数字显示「上次连续 N 天」，提示「今天还没打卡」
- **AC-3**：断签重置后 N 归零；补卡成功后正确重算 streak

### US-TASK-04：截止前 1 小时收到提醒

> 作为**忙碌白领小林**，我需要**在重要任务截止前 1 小时收到 Web Push**，以便于**不会因为忙忘了关键节点**。

**验收标准（AC）**：
- **AC-1**：任务设置了 `due_at` 且未完成，在 `due_at - 1h` 触发 Web Push（前提：用户已订阅推送）
- **AC-2**：Push 通知标题「⏰ 任务即将到期」，正文显示任务标题
- **AC-3**：点击 Push 通知直接跳转到该任务详情页

### US-HABIT-01：补卡挽救断签

> 作为**自我提升者阿瑶**，我需要**为昨天忘打的卡补上**，以便于**避免一次失误就让连续记录归零**。

**验收标准（AC）**：
- **AC-1**：习惯详情页提供「补卡」入口，仅展示最近 3 天日期可选
- **AC-2**：补卡成功后 streak 重新计算并立即更新 UI
- **AC-3**：超过 3 天的日期按钮置灰，不可点击（前端 + 后端双重校验）

## 6. 功能范围与边界

### In Scope（MVP 交付）

- 任务的 CRUD、软删除、30 天回收站
- 列表视图（今日/本周/全部）+ 看板视图（按状态/优先级）
- 子任务（一层）、标签（≤5 个）、优先级 P0-P3
- 习惯的 CRUD、打卡、断签补卡（≤3 天）、streak 统计
- 截止时间 Web Push（提前 1 小时）
- 习惯漏签提醒（21:00）

### Out of Scope（明确不做）

- **不做**：无限层级子任务（v1.1+ 再考虑）
- **不做**：任务评论 / 多人协作 / 共享看板（v1.2 占位）
- **不做**：番茄钟 / 时间块（v1.3）
- **不做**：智能排期 / 标题改写（v1.1，需先看 LLM 实际效果）
- **不做**：任务导入（CSV / 剪贴板）（v1.3）
- **不做**：任务与日历（Google Calendar / Outlook）双向同步

## 7. 成功指标（KPIs）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 任务创建端到端耗时 P95 | ≤ 1.5s | 前端埋点 + 服务端日志 |
| 习惯打卡点击成功率 | ≥ 99% | 点击埋点 / 成功埋点 |
| 周留存（连续 7 天打开过任务模块） | ≥ 50% | 后端用户行为日志 |
| 习惯完成率月均 | ≥ 70% | `(打卡次数 / 应打卡次数)` 聚合 |
| Push 送达率 | ≥ 90% | Web Push 服务端回执 |
| 模块 NPS（季度调研） | ≥ 40 | 季度内嵌问卷 |

## 8. 风险与应对

| 风险 | 影响 | 概率 | 应对 |
|---|---|---|---|
| **Web Push 在 iOS Safari 兼容性差** | 高 | 高 | 提供应用内「通知中心」作为降级；研究 iOS 16.4+ 的 Web Push 行为；后续可加邮件兜底 |
| **Streak 计算在用户跨时区时出错** | 中 | 中 | 所有时间存 UTC + 用户时区；streak 计算按用户时区的「自然日」 |
| **补卡接口被滥用（绕过 3 天限制）** | 中 | 中 | 后端强校验 `backfill_date >= today - 3 AND backfill_date < today`（即补卡窗口为 `[today-3, today)`，与 §3 HABIT-005 与 US-HABIT-01 AC-1 的「最近 3 天」保持一致）；前端只渲染这 3 天日期选项作为前端校验；限流（同习惯每天 5 次补卡请求） |
| **回收站 30 天后被清理导致用户投诉** | 中 | 低 | 清理前 3 天应用内 Banner 提醒；提供「恢复」入口直到清理日 |
| **子任务层级被需求方扩展到无限层级** | 中 | 中 | 数据库 schema 预留 `parent_id`，但前端只渲染一层；v1.1 重构前加限流校验 |
